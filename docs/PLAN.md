# 魔法运动会 Online：开发计划

> 依据：`research-rules.md`（规则与 36 名角色）、`research-cloudflare.md`（免费层限制与架构）、`research-frontend.md`（渲染、美术、音效、体积）。
> 目标：做一款精致、体积小、能在 Cloudflare Workers 免费计划上跑的在线版 Magical Athlete，支持注册、大厅、断线重连、AI 补位，以及基础包全部 36 名角色。

## 2. 总体架构

```
浏览器 (Preact + signals; three 按需加载)
   │  HTTPS /api/*          WebSocket /ws/lobby, /ws/room/:id
   ▼
Worker 入口 (路由、验签 Cookie、限流)
   ├─ 静态资源 (Workers Static Assets，免费且不计请求)
   ├─ D1: users / sessions黑名单(可选) / match_results
   ├─ LobbyDO (全局单例)：房间摘要表 + 大厅 WS 广播
   └─ RoomDO (每房间一个，SQLite)：权威游戏状态 + 房内 WS (Hibernation) + alarm 计时 + AI
```

关键原则：
- **服务端权威**：掷骰（带种子的 RNG）、规则结算、AI 都在 RoomDO 里跑，客户端只发「意图」，只负责播放事件动画。
- **规则引擎是纯 TS 包**（`packages/engine`）：没有 I/O，服务端和测试共用，客户端也可以用它做离线演示或回放。
- **事件驱动动画**：引擎每一步输出 `GameEvent[]`（`roll`、`move{path}`、`warp`、`trip`、`ability{id}`、`score`、`eliminate`、`finish`……）。客户端按队列逐个播放，所以动画和规则天然一致。
- **只让 `/api/*`、`/ws/*` 进入 Worker**，其余都走静态资源，额度用完时页面照样能打开。

## 3. 规则引擎设计（核心难点）

36 名角色之间的连锁触发是整个项目最难的部分，引擎要单独做扎实。

1. **状态**：`GameState`，包含阶段（lobby / draft / pick / race / between / end）、选秀牌池、每人手牌、本场赛道、棋子位置/是否摔倒/是否淘汰、筹码、行动顺序、RNG 状态、`pending`（等某个玩家做选择）。
2. **动作**：`Action`，例如 `draftPick`、`chooseRacer`、`roll`、`useAbility{choice}`、`decline`、`predict`……
3. **结算模型**：
   - **触发队列**：每个原子效果（移动一格、停下、经过、掷骰……）发出领域事件，各能力订阅这些事件。
   - **排序**：按规则书优先级排，赛道格先结算，然后是当前玩家，然后其他人顺时针。
   - **同时到达**：「同时到达」作为一组处理，组内的人互相不触发停格能力（2026-08 修订）。
   - **防死循环**：循环保护（同一状态签名重复出现即停止），Scoocher 和 Suckerfish 的反复互动按规则书豁免；另设硬上限 500 步。
4. **玩家选择**（可选能力和需要目标的能力）：
   - 引擎遇到可选能力时**暂停**，写入 `pending{player, kind, options, deadline}`。
   - RoomDO 设 alarm 计时（默认 20 秒），超时按默认选项处理：可选能力默认不发动，需要目标的能力交给 AI 决定。
   - 只有当前「有意义」的选择才会问玩家，例如 Dicemonger 的重掷只在可用时提示，避免每回合弹一堆问题。
5. **能力实现方式**：每个角色一个模块，形如 `{ id, hooks: { beforeMainMove, onRoll, onPass, onStop, onOtherPower, ... }, ai: {...} }`。Copy Cat、Egg、Twin 通过「当前生效能力」这一层间接引用其他角色。
6. **测试**（Vitest）：
   - 每个角色至少 3 个单元用例，覆盖规则书注释和 FAQ 中的每条互动。
   - **模糊测试**：AI 互相对战 10 万局随机组合，断言不崩溃、不死循环、分数守恒，且每局都能结束。
   - 规则调研中「未找到」的点（Blimp 弯道=15 号格、Copy Cat 自己独自领先时没有能力等）集中写在 `rules-decisions.md`，代码里引用条目编号。

## 4. AI 补位

- **简单**：随机选秀和派人；可选能力 50% 概率发动。
- **普通**：
  - **选秀**：参考角色强度表（模拟数据生成），再按已选阵容做一点组合调整。
  - **派人**：强角色留到后面分值高的场次。
  - **比赛中**：可选能力用一步前瞻判断。例如 Legs 判断「固定走 5」的期望值是否高于掷骰（5 > 3.5 时发动）；Rocket Scientist 要掂量翻倍和摔倒的代价；Flip Flop 和领先者换位置；Genius 预测出现最多的点数。
- **角色强度表**：用引擎离线跑大量模拟算出每个角色的平均得分，生成 `tier.json`。既给 AI 用，也作为平衡参考。
- **托管**：真人掉线超过 30 秒（可配置），当到他行动时由 AI 代打；重连后立刻交还。

## 5. 服务端细节

### 5.1 账号
- **注册**：用户名唯一（D1 唯一索引），密码用 PBKDF2-SHA256 哈希，迭代 6 万次左右（10 万次会压线超过 10ms CPU）。哈希串里记下参数，以后可以升级。
- **会话**：`sid` Cookie，内容是 `userId.expiry.HMAC`，HttpOnly、Secure、SameSite=Lax，有效期 30 天。验证不查库。
- **限流**：登录和注册接口按 IP 限流，用一个轻量 DO 计数，或者直接用 Workers 的 Rate Limiting binding（免费）。

### 5.2 LobbyDO
- 内存加 SQLite 存房间摘要（id、名称、人数/上限、状态、是否私密）。
- RoomDO 状态变化时调用 LobbyDO 更新摘要；大厅的 WebSocket 推增量。

### 5.3 RoomDO
- **持久化**：游戏状态序列化后存一行，`seq` 递增。每次完整动作结算后写一次，不在每个小步骤后写，以节省「行写入」这个最先耗尽的额度。
- **WebSocket**：用 Hibernation API；`serializeAttachment` 存 `{userId, seat}`；心跳用 `setWebSocketAutoResponse`，不唤醒对象。
- **重连**：客户端带 `lastSeq` 来；服务端回完整快照加之后的事件（或只回快照），客户端跳过动画直接对齐。
- **alarm**：同一时间只保留一个最近的截止时间，涵盖行动超时、AI 思考延迟（让 AI 看起来像人，0.6–1.2 秒）、掉线宽限和房间回收。
- **回收**：对局结束或空房 10 分钟后 `deleteAll()`，结果写进 D1 的 `match_results`。

### 5.4 免费额度
最先耗尽的是 DO 行写入：约 600 局/天，优化后可到约 1,500 局/天，自己和朋友玩绰绰有余。额度用完时 RoomDO 捕获错误，给客户端显示「今日服务器额度已用完」。

## 6. 前端

### 6.1 技术栈与体积预算
| 部分 | 选择 | 体积（gzip） |
|---|---|---|
| UI | Preact + @preact/signals | 约 8 KB |
| 构建 | Vite；three 单独分块，进对局时才加载 | — |
| 3D | three r186，按需导入 | 约 132 KB |
| 动效 | 自写 tween，约 1 KB；冲线彩带用 instanced mesh 自己做 | ~1 KB |
| 音效 | ZzFX（程序合成）+ 3–5 个 Kenney CC0 采样（Opus/ogg）| ~1 KB + 约 60 KB |
| BGM | ZzFXM 原创小调循环（大厅一首、比赛一首）| < 3 KB |
| 字体 | 正文用系统字体；标题用得意黑，只保留用到的字 | 约 40 KB |

预算：大厅首屏 JS ≤ 40 KB，对局 JS 合计 ≤ 220 KB，所有资源 ≤ 600 KB。

### 6.2 场景与动效
- **视角**：2.5D 斜俯视的「浮空小岛」赛道，30 格（起点加 1–29 号，再加冲线台），沿 S 形弯道排布，相机做平移跟随。温和面草地，狂野面熔岩或沼泽。特殊格用浮雕图标标出：箭头、香蕉皮式摔倒格、星星。
- **棋子**：36 名角色都用基础几何体拼装（胶囊、球、锥、环），加卡通着色和描边。每个角色一份参数配方（体型、配色、配件），保证剪影各不相同。不加载 glTF，全部代码生成。
- **骰子**：服务端先定点数。客户端随机播放一条预先录好的 cannon-es 投掷轨迹，再把骰子模型预先旋转一下，让它落地时朝上的正好是那个点数。有摇骰音和落桌音。
- **移动**：
  - 逐格做抛物线跳，起跳落地时压扁再弹回，落地有尘土粒子。
  - 后退时转身跳；瞬移是缩小、闪光、在目标处弹出；摔倒是翻倒加冒星星。
  - 被淘汰（M.O.U.T.H. 吃掉）时有咬合动画，棋子飞出场外。
- **能力触发**：角色头像加上能力名的漫画拟声字（如「DUEL!」「POOF」）在棋子上方弹出，同时侧边栏的事件日志记一条。
- **播放速度**：事件队列支持 1×、2× 和跳过。断线重连或在后台标签页时直接跳到最终状态。

### 6.3 页面
1. **登录/注册**。
2. **大厅**：房间卡片、建房对话框、快速加入。
3. **房间**：6 个座位，每个座位可以是空位、真人或 AI，房主可以切换。
4. **选秀**：翻开的卡牌桌面，蛇形顺序提示，轮到谁有倒计时环。
5. **派人**：从自己 4 张手牌里暗选，所有人选完后一起翻开。
6. **比赛**：3D 赛道占主体。底部是自己的手牌和操作区（掷骰按钮、能力选择）；顶部是比分条；侧边是事件日志。
7. **场间结算**：领奖台和筹码飞入动画。
8. **终局结算**：总分排名，可以「再来一局」。

另有「图鉴」页可以查看 36 名角色的能力，在对局中长按棋子也能看。

### 6.4 美术
- **风格**：低多边形的「贴纸卡通」风。
- **色板**：魔法紫 `#6C4BF4`、夜幕 `#2B1B4D`、冲线橙 `#FF7A2F`、星光黄 `#FFD23F`；外加 6 个玩家色。
- **卡牌头像**：程序生成的 SVG，由角色配方渲染，和 3D 棋子保持一致。
- **图标**：game-icons.net（CC BY 3.0，需要在「致谢」页署名）。
- **UI 和粒子**：Kenney（CC0）。
- **表情反应**：Fluent Emoji（MIT）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 角色连锁触发复杂，容易出 bug 或死循环 | 统一的触发队列和优先级、循环保护、模糊测试、`rules-decisions.md` 记录所有裁定 |
| 免费层 DO 的 CPU 上限（可能 10ms）| 一次动作的结算是纯内存计算，通常远低于 1ms；AI 不做深度搜索 |
| DO 行写入额度 | 一个动作只写一次；alarm 合并设置；必要时只在回合结束时落盘 |
| 部署时所有 WebSocket 断开 | 客户端指数退避重连，状态从 SQLite 完整恢复 |
| PBKDF2 CPU 超限 | 迭代次数做成可配置，上线后观察 CPU 时间 |
| 版权：游戏名、角色名、规则文本属于原出版商 | 美术全部原创；页面标注「非官方同人作品、非商业」；能力描述用自己的话改写；见下方待定 1 |
| iOS Safari 的音频解锁和 Opus 兼容 | 首次点击时解锁 AudioContext；采样同时准备 m4a 备份 |
